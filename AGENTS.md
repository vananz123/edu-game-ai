# Instructions for AI agents working on EduGame Studio

## Read first
1. `docs/AGENT_HANDOFF.md`
2. `docs/PROJECT_BRIEF.md`
3. `docs/ARCHITECTURE.md`
4. `docs/STATUS.md`
5. `docs/ROADMAP.md` and `docs/DECISIONS.md`

## Product direction
- EduGame Studio is a Windows desktop application for teachers to create educational games from lesson plans and documents.
- TypeScript is the source language. Keep new application/backend code in TypeScript unless a dependency requires otherwise.
- Games that have already been saved must play offline. Cloud AI is only needed to generate new content; never make gameplay depend on internet access.
- Prefer fixed, tested game engines fed by validated structured game data. Do not execute arbitrary JavaScript/HTML generated by a model.
- Target product model: free tier + paid tier; first pilot is 1–10 teachers.

## Engineering rules
- Before changing code, inspect the relevant files and run the existing checks when possible.
- Do not claim a feature works unless you have run a relevant test or clearly label it unverified.
- Keep API provider secrets (`GEMINI_API_KEY`, Supabase service-role key) on the backend only. Never put product-owned secrets in Electron, renderer code, installer, or repository.
- Do not remove SQLite migration, `.egame` import/export, or offline behavior without explicit approval.
- Avoid broad rewrites. Make small, reviewable changes and add tests for behavior changes.
- Do not add paid services or payment integrations without explaining cost and asking for approval when the decision is consequential.
- Never use real student personal data in tests. Use synthetic examples.

## Required handoff after each task
Update `docs/STATUS.md` and, if decisions or sequencing changed, `docs/DECISIONS.md` / `docs/ROADMAP.md`. Report:
1. files changed;
2. behavior implemented;
3. exact commands run and their results;
4. what remains unverified;
5. next recommended task.
